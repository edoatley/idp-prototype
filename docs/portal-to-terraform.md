# From portal form to Terraform: the write path

How a four-field web form becomes a real, compliant GCS bucket — the mechanism, not the tour.
For the guided, screenshot-led version see [`docs/walkthrough/`](./walkthrough/README.md);
for *why* each decision was made, see [`EVALUATION.md`](../EVALUATION.md).

> **The short version.** There are no template files. The Terraform is two template literals
> inside [`idp-portal/src/generator.ts`](../idp-portal/src/generator.ts), and the portal never
> writes to disk — it commits straight to GitHub through the git data API.

```
form  →  validate  →  request-id  →  generate  →  one commit on a portal/* branch  →  PR
                                                                                      │
                                          pr.yml: plan + policy gate + sticky comment ┘
                                                                                      │
                                            merge → apply.yml: WIF apply + audit comment
```

## 1. The form

`POST /buckets` ([`server.ts:150-192`](../idp-portal/src/server.ts)) takes exactly four fields:

| Field | Source of options | Validated by |
|---|---|---|
| `name` | free text | `NAME_RE` in [`validate.ts:19`](../idp-portal/src/validate.ts) |
| `owning_team` | `<select>` from `platform/teams.yaml` | membership check, `validate.ts:38` |
| `environment` | `<select>` from `platform/config.yaml` | membership check, `validate.ts:31` |
| `requester` | free text (GitHub handle) | non-empty, `server.ts:159` |

`NAME_RE` (`/^[a-z0-9][a-z0-9-]{1,28}[a-z0-9]$/`) is a deliberate copy of the module's own
rule at `modules/gcs-bucket/variables.tf:10`. The duplication is intentional: the portal
fails fast with an inline form error, and the module still rejects a hand-written stack that
bypasses the portal entirely.

Ownership is checked twice for the same reason — once in the portal for the dropdown, and
once in Terraform as a resource *precondition* (`modules/gcs-bucket/main.tf:62-65`), because
a variable `validation` block cannot read a file.

## 2. The request id

[`requestId.ts:21-26`](../idp-portal/src/requestId.ts) mints
`req-<YYYYMMDD>-<team>-<name>-<4 random base36 chars>`, e.g.
`req-20260903-payments-discounts-z0of`. The charset is chosen so the value is a legal GCS
label (`^[a-z0-9_-]{1,63}$`) — it ends up as the mandatory `request-id` label on the bucket,
which is what ties a live resource back to the PR that asked for it.

## 3. Generation — where the templates live

**Nowhere but `generator.ts`.** There is no `templates/` directory, no `.hbs`, no `.tmpl`.
`main.tf` is the template literal at [`generator.ts:34-72`](../idp-portal/src/generator.ts)
and `metadata.yaml` at `generator.ts:74-83`.

**Why inline literals rather than a template engine:** the literals are pre-aligned to
`terraform fmt` output. Every HCL block key here is fixed-width, so the alignment is constant
no matter how long the *values* are (they are all quoted strings). That means every generated
stack is `fmt`-clean on arrival — which matters because `pr.yml` runs `terraform fmt -check`
and would otherwise fail every portal-raised PR. A templating engine would make that property
much harder to guarantee.

`generate()` is a pure function — no I/O, no network — so it is trivially unit-tested
(`idp-portal/tests/`). `github.ts` is the only side-effecting module.

### What gets derived

From `generator.ts:29-32`, for `name=discounts, owning_team=payments, environment=dev`:

| Value | Expression | Example |
|---|---|---|
| `dirName` | `${owning_team}-${name}` | `payments-discounts` |
| `prefix` — the Terraform **state** prefix | `stacks/${environment}/${dirName}` | `stacks/dev/payments-discounts` |
| `stackDir` — the repo path | `idp-gitops/${prefix}` | `idp-gitops/stacks/dev/payments-discounts` |
| `bucketName` | `edo-${env}-${team}-${name}` lowercased | `edo-dev-payments-discounts` |

`bucketName` here is **display-only** — it names the PR and the success page. The
authoritative name is computed in Terraform at `modules/gcs-bucket/main.tf:23`.

### The two generated files

Exactly two, every time. Here is the live stack
[`idp-gitops/stacks/dev/payments-discounts/main.tf`](../idp-gitops/stacks/dev/payments-discounts/main.tf),
verbatim:

```hcl
# Generated by idp-portal — do not edit by hand.
# Provisioned via the golden path: pr.yml plans + gates this, apply.yml applies on merge.
# State lives under its own prefix in the shared state bucket, isolating each request.

terraform {
  required_version = ">= 1.5"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 6.0"
    }
  }

  backend "gcs" {
    bucket = "idp-prototype-edo-tfstate"
    prefix = "stacks/dev/payments-discounts"
  }
}

provider "google" {
  project = "idp-prototype-edo"
  region  = "europe-west2"
}

module "bucket" {
  source = "../../../modules/gcs-bucket"

  name        = "discounts"
  owning_team = "payments"
  environment = "dev"
  request_id  = "req-20260903-payments-discounts-z0of"
}

output "bucket_name" {
  description = "Name of the provisioned bucket."
  value       = module.bucket.bucket_name
}
```

Three things in there carry more weight than they look:

- **The `backend "gcs"` block is the whole isolation story.** Each request gets its own state
  prefix in the one shared state bucket, so a broken apply on one stack cannot corrupt
  another, and each stack is a self-contained Terraform root that `terraform -chdir=<stack>`
  can init/plan/apply on its own. There is no separate backend file and no `-backend-config`
  flag anywhere in CI — it is inline, and it is generated.
- **Only four inputs are passed to the module.** Everything else — region, uniform
  bucket-level access, public-access prevention, versioning, `force_destroy = false`, the
  lifecycle rule, the four mandatory labels — is non-overridable inside the module. That is
  the "platform enforces the safe defaults, devs pick very little" principle made concrete.
- **`output "bucket_name"`** exists so `apply.yml` can read it back out of
  `terraform output -json` and name the bucket in its audit comment.

And `metadata.yaml` — the inventory record the Phase 5 dashboard reads:

```yaml
# Generated by idp-portal — the canonical inventory record for this request.
# The apply pipeline provisions the infrastructure; this file is the durable,
# human-readable source of truth the visibility dashboard (Phase 5) aggregates.
type: gcs-bucket
owning_team: payments
environment: dev
request_id: req-20260903-payments-discounts-z0of
requester: edoatley
created_at: "2026-09-03"
```

`created_at` is quoted so YAML keeps it a string. `inventory.ts:32` requires this file to
exist for a stack to appear in the dashboard at all — a directory with only a `main.tf` is
invisible to the read path.

## 4. Opening the PR — the API sequence

No clone, no working directory, no `git` binary. `github.ts` uses a ~18-line REST client over
built-in `fetch` ([`github.ts:21-39`](../idp-portal/src/github.ts)) — deliberately not
Octokit (see `EVALUATION.md` on the ESM/CJS friction).

First, a collision guard (`github.ts:89-95`):

```
GET /repos/{owner}/{repo}/contents/{stackDir}?ref=main
    2xx → throw "stack ... already exists — pick a different name."
    404 → carry on
    else → throw "unexpected status N ..."
```

Then one commit, built entirely through the git data API (`github.ts:48-69`):

| # | Call | Purpose |
|---|---|---|
| 1 | `GET /git/ref/heads/main` | base sha |
| 2 | `GET /git/commits/{baseSha}` | base tree sha |
| 3 | `POST /git/trees` | new tree: `base_tree` + one blob per generated file |
| 4 | `POST /git/commits` | commit with `parents: [baseSha]` |
| 5 | `POST /git/refs` | create `refs/heads/portal/<env>-<team>-<name>` |
| 6 | `POST /pulls` | open the PR against `main` |

### The naming conventions — and why they are load-bearing

| Thing | Value |
|---|---|
| Branch | `portal/<env>-<team>-<name>` — e.g. `portal/dev-payments-discounts` |
| Decommission branch | `portal/decommission-<env>-<team>-<name>` |
| PR title **and commit message** (they are the same string, `github.ts:57`) | `Provision bucket edo-dev-payments-discounts` |
| Decommission title | `Decommission bucket edo-dev-payments-discounts` |
| Base | `main` |

These are not cosmetic. `metrics.ts:34-36` identifies which PRs are platform requests — and
therefore which ones count toward lead-time and delivery metrics — by matching
`/^(Provision|Decommission) bucket/i` on the title **or** a head ref starting `portal/`.
Change the wording in `server.ts` and the dashboard quietly stops counting.

The PR body is:

```
Requested via idp-portal by @<requester>.

Stack: `idp-gitops/stacks/dev/payments-discounts` · request-id `req-20260903-...`.

PR CI will plan + run the policy gate; merge to provision via WIF.
```

The token is a fine-grained PAT with **Contents** and **Pull requests** read/write — Contents
covers calls 1-5, Pull requests covers call 6. The dashboard adds read-only
`/actions/.../runs` and `/issues` calls on top. The portal never holds GCP credentials; only
CI does, and keylessly via WIF.

## 5. What CI does with it

`pr.yml` triggers on `idp-gitops/stacks/**`, detects the changed stack, and runs
`fmt -check` → `init` → `validate` → `plan` → `conftest test` against the plan JSON. A policy
deny fails the job and blocks the merge. The result lands as a sticky PR comment.

On merge, `apply.yml` authenticates via Workload Identity Federation, applies, and posts the
outcome back onto the originating PR (it runs on `push`, so it looks the PR up from the merge
commit). See [`walkthrough/04`](./walkthrough/04-pr-plan-and-policy-gate.md) and
[`walkthrough/05`](./walkthrough/05-apply-and-audit.md).

## 6. Decommission

The same machinery, inverted. `openDecommissionPR` (`github.ts:122-133`) builds the identical
tree → commit → ref → PR sequence, but with `sha: null` tree entries for `main.tf` and
`metadata.yaml` — which deletes those paths relative to `base_tree`. Deleting the stack
directory *is* the delete request; that is what makes it GitOps-consistent.

On merge, `destroy.yml` picks it up with `--diff-filter=D` and the inverted "does `main.tf`
exist" test — the exact complement of what `apply.yml` looks for, so the two pipelines never
act on the same stack. It restores the deleted config from the parent commit (Terraform needs
the backend and module blocks in order to destroy), then destroys.

`force_destroy = false` in the module means a non-empty bucket fails the destroy loudly
rather than silently deleting data.

## 7. Sharp edges worth knowing

- **`config.yaml`'s `org_prefix` and `default_region` are loaded but never used.**
  `config.ts:26-41` parses them, and nothing reads them. The `edo-` prefix is hardcoded at
  `generator.ts:32` and again at `inventory.ts:43`; the region at `generator.ts:14` and again
  in the module. Editing `platform/config.yaml` alone will silently do nothing — you must
  change all four sites. (`environments` and `teams.yaml` *are* genuinely read.)
- **A decommission PR gets no plan and no policy comment.** `pr.yml`'s detection requires
  `main.tf` to exist, so a stack-removal PR yields an empty matrix and the plan job is
  skipped. There is no pre-merge preview of what is about to be destroyed — you see it only
  in the destroy run afterwards.
- **The git-data calls are not status-checked.** Only the collision guard inspects `status`;
  calls 1-6 do not. A pre-existing branch (say, a retried request after a failed attempt)
  returns 422 and surfaces as a confusing downstream error rather than a clean message.
- **The collision guard covers the stack directory, not the branch.**
